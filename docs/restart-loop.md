# Restart loop of the build from C (2026-11-01)

The movable build of Virtua Tennis (every game function from C, relinked, `make c` then a Pluto disc) shows the BIOS licence
screen, then a white screen, then resets about every 15.6 s, forever. The original disc does not. This file keeps what was
established, what was ruled out, what was changed and what is open, so the next session starts here and not from memory.
Nothing below is committed. Update this file whenever a lead is closed or opened.

## What the symptom is

- Flycast log: `SB/HOLLY: System reset requested` every 15.6 s. Breakpoints are void in Flycast here (sampling and small memory
  reads only; bulk `m` reads return scattered zeros, so never diff dumps made that way).
- The BIOS licence screen runs before `1ST_READ.BIN`; "after the licence" means the game's first instruction ran.
- The original runs on to `kmyStartRender`; the build does not. `tools/sh4sim.py` stops at Kamui's PVR wait, so it has never
  reached the code that polls the pad.

## How the game leaves for the BIOS (read from the C and the asm)

| Path | Where | Condition |
|---|---|---|
| `mainExitToBios` -> `syBtExit` | `mainCheckDrive` (`src/gen_e.c`) | the counter at `0x8C12C5A0` counts down to 1 |
| `mainExitToBios` | `mainCheckReset` | mode `0x8C20D14C` is 7 and the start bit of a pad is down (pad array `0x8C29B898`) |
| `mainSoftReset(1)` | `mainCheckReset`, and the start-bit tests of the screen code at `8c02ec56` | game restart (files closed, game mode reloaded), not the BIOS |

The counter is armed only by `FUN_8c010dc8` (`src/gen_aaz.c` now), the GD-ROM drive-error callback that `sysInit` registers
with `gdFsEntryErrFuncAll(0x8C010DC8, 0)`. In the original a drive error exits to the BIOS two frames later.

## Found and fixed: dropped arguments at table-jump trampolines

`gdFsEntryErrFuncAll` and `gdFsOpenRange` are `mov #off,r0; mov.l @(r0,r14),r0; jmp @r0`: a jump through the file system's
table. Their target is read from memory, so the arity scan cannot name it and wrote null (unknown). `_combine_def` in
`gen_core.py` then took the trampoline's own generated definition, a `(void)`, as its arity. Callers were generated without
their arguments and the proof compared them on none (so `sysInit` was EQUIVALENT at 202 of 203 instructions).

| Call | Original | C before | Effect |
|---|---|---|---|
| `sysInit` -> `gdFsEntryErrFuncAll` | r4 = `0x8C010DC8`, r5 = 0 | none | a leftover r4 (12) registered as the callback |
| `ADXSTM_OpenRange` -> `gdFsOpenRange` | r4 = a4, r5 = a5 | none | a file range opened from leftover registers |

Found by reading the built image (r4 = 12 at the call), not by the checks. The cause was confirmed in the tool code, the
tool was fixed in the skill, and the calls were regenerated by the fixed tool (no hand edit left):

- Skill (`~/workspace/skills/dc-decomp-kickoff`, uncommitted): `gen_core.py` (an unresolved pass-through stays unknown,
  `"pass-through"` in `state/arity_scan.json`, null entries are rescanned), `tests/arity/check.py` (reproduces the bug with
  stand-in disassembly; fails on the old code), `SKILL.md` step 8 item 2, `references/evidence.md`, `template/AGENTS.md`.
- This repo: `tools/5-generated/gen_equiv/gen_core.py` and `AGENTS.md` copied from the skill. CT and ZR do not have it yet
  (user: only VT until it is fixed).
- Regeneration: `python3 tools/5-generated/gen_equiv --regen <names>`: round 1 `sysInit ADXSTM_OpenRange` (37 s), round 2 the 18
  unknown-arity trampolines and their C callers (23 proven, `adxf_LoadData` kept its old C: no cases, the original does not
  finish on them), round 3 four callers found by grepping the C (`gdFsChangeDir`, `mwRnaInit`, `thunk_ADXERR_EntryErrFunc`,
  `thunk_mwRnaErrEntryFunc`; 4 proven). Logs: `build/regen_arity.log`, `regen_arity2.log`, `regen_arity3.log`.
- Hand-written C that the regeneration skips (`ADXSTM_GetFad`, `GetFsizeByte`, `GetFsizeSct`, `gdFsOpen`, `gdFsOpenRange`,
  `gdFsGetDrvStat`, `mwRnaErrEntryFunc`) was read against the asm by hand: all match.

Result: the Pluto build with these fixes (10:36 disc, `build/disc-cbuild`) still loops. The fixes are real but not the cause,
or not the only one.

## Open leads

1. **Which exit fires.** Only a run shows it: `sh4sim` past the PVR wait on the built image and the original (log which of
   `mainExitToBios` / `mainSoftReset` is reached and the pad words at `0x8C29B898` each pass), or Flycast samples. Needs the
   user's go (a run of minutes).
2. **File opens by name after the move.** The game opens `texture_SSELE_stage_select.bin` by name through the file system.
   Whether its directory lookup copes with a file outside the usual track range is unverified.
3. **Calls the argument checks do not reach:** function-pointer calls, callers that are still assembly pieces (original code,
   so correct by construction), and `nlObjPut_vtxcolbridge` (no C call found).
4. **Whole-game comparison of every direct call** (the original's r4-r7 setup before each call against the C's argument
   count). First pass: 3,898 functions, 16 direct callees flagged, 1,223 "no C call found" (the C matcher does not know every
   call form), indirect calls too noisy to use. Two boot-path hits (`sysInit` -> `nlInitInterruptDC`, `sysInitGraphics` ->
   `nlSysUseLatency2V`) were false positives: a delay slot of the previous call counted as setup. The check ignores delay slots
   of the branch before (fixed in the script), after which these 16 remain and are NOT yet read by hand (caller -> callee, the
   original's count vs the C's): `FUN_8c010da8` -> `strmExec` 1 vs 0; `matchExec` -> `playerStartReactions` (one site 3 vs 2);
   `FUN_8c084302` -> `umpCallSpareA` 1 vs 0; `FUN_8c0843e8` -> `umpCallSpareB` 1 vs 0; `FUN_8c08b218` and `FUN_8c08b24c` ->
   `shadowVolPutDirA` 1 vs 0; `FUN_8c08d78c` -> `shadowNullCb` 1,1 vs 0,0; `FUN_8c0b5f78` -> `dbgMenuGetSelect` (one site 3 vs 0)
   and `restart_t404` 1x4 vs 0; `matchSceneInit` -> `crowdSetup` 1 vs 0; `FUN_8c0bdf26` -> `emotRetOne` 3,3 vs 0,0;
   `FUN_8c0e426a` -> `seSystemApply` 1 vs 0; `syCfgSetSoundMode` -> `syBtCfgSet` 2 vs 1; `adxt_start_sj` -> `ADXSJD_Start`
   1 vs 0; `SJUNI_Create` -> `SJUNI_Reset` 4 vs 1; `kmiFLWCTRLCheckTimeOut` -> `kmyCreateRegionArray` 1 vs 0. Many are probably
   callees that read r4 only to pass it on, or a register still holding the caller's own argument; each needs a hand read of
   the asm around the call (`python3 tools/shdis.py --func <caller>`, find the `jsr`, read the registers set before it and in
   its delay slot). `syBtCfgSet` and `SJUNI_Reset` are the likeliest real ones (a count below, not zero).

## Method notes (so the checks can be repeated)

- Call-site comparison: for each `jsr @rN` whose register was loaded from a pool word naming a function (or each `bsr`), collect
  the writes to r4-r7 in the instructions before it back to the previous branch, and in its delay slot; stop before a delay slot
  that belongs to the branch before. Compare the highest register set with the number of arguments of the C call of the same
  callee in the same function. A heuristic: it misses arguments passed through untouched (false negatives) and overcounts when
  a register is set for another reason (false positives). It is not a tool of the repo and must not become one: the real fix
  is in `callee_arity` / `equiv.py` (see the skill's `references/evidence.md`, entry of 2026-11-01).
- The generator's `ind` (indirect call) path already passes what the caller set for an unknown callee; the bug was only that
  "unknown" was replaced by the `(void)` definition.
- Rule from the user: nothing is committed until the build works, then the tooling is improved (CT and ZR get the fix after VT).

## Stale C is a second source of dropped arguments (found 2026-11-01 10:41)

`syBtCfgSet(item, value)` reads three argument registers (scan `[3, 0]`), yet `syCfgSetSoundMode` and `syCfgGetSoundMode`
called it with one: the old C even loaded `*0x8C20C240` into a local and never used it, where the original puts it in r5.
`gen_equiv --regen syCfgSetSoundMode syCfgGetSoundMode` (21 s, both proven) now writes `syBtCfgSet(0x2, *(int *)0x8C20C240, a6)`:
the current generator is right and the C was output of an older generator that no step revisited (the same shape as
`netJudgeExec`'s tail duplication in the findings notes). So the arity scan alone does not find every dropped argument:
any function whose C predates the generator's current argument rules can drop them, whatever the callee. The call-site
comparison below is how those are found; regenerating the flagged function is how they are fixed (no hand edit).
`syBtCfgSet` is the BIOS flash configuration call (it runs `fmMngInit` / `fmMngFormat`), with r5 a buffer pointer: a leftover
r5 there writes through a stale pointer.

## Steps, emulator (Flycast GDB), and what it can and cannot do

Source: `references/evidence.md` of the skill, the notes of 2026-10-23/24/30 and this repo's sessions of 2026-10-30/11-01. Tools:
`scripts/flycast_gdb.py` (`sample`, `mem`, `snap`, `bp`) in the workspace repo, `scripts/gdbsnap.py` in the skill (`snap`,
`timeline`, `diff`). The GDB build is `~/Applications/Flycast GDB.app` started with `-config config:Debug.GDBEnabled=yes`
(port 3263); the release builds have no GDB server.

Can do:
- Run the built disc and see whether and when it resets: the Flycast log line `SB/HOLLY: System reset requested` gives the
  reset time and period (here 15.6 s).
- Sample the program counter and registers every fraction of a second (`flycast_gdb.py sample`) and see which function the
  game is in, and read small memory ranges at known addresses (`mem`), read at the `0C...` mirror, not `8C...`.
- Stop when the pc enters a range (`snap` or `bp --in lo hi`), then write every register and RAM: for example stop on
  `mainExitToBios` and read the pad words at `0x8C29B898` (read as `0x0C29B898` + the build's shift) and the drive counter.
- Software breakpoints work only if placed after the game is loaded (`bp --after <seconds>`); each address logs its first hit.

Cannot do, or gives wrong results (do not rely on it):
- Breakpoints placed before the game has loaded are overwritten by the loader (0 hits); in some runs breakpoints never fired
  at all in this build, with or without the dynarec. Sampling is the dependable method.
- Bulk memory reads (many 0x800-byte `m` chunks in a row) return scattered zero bytes: never diff two big dumps made that way.
  The "578 KB overwrite" of 2026-10-30 was this artifact. Check any dump against a small read of an address the CPU is executing.
- The first ~15 s of pc samples are the BIOS's own programs (same pcs on every disc): never read them as game code.
- This build boots with reios (no real BIOS), so BIOS behaviour (what `syBtExit` really does, the licence screen) may differ
  from a console; a reset seen here is a Holly reset, not proof of the real BIOS path.
- It cannot take pad input: the pad is the user's. Never drive the keyboard or mouse (user rule); a test that needs a
  button press is the user's to do.
- No game-specific savestates here; the run starts from boot each time. Runs are not a bisection loop (user rule): one run per
  question, the question written down first.
- If the game freezes the emulator, close it and read what was captured; never wait on it in a polling loop.
